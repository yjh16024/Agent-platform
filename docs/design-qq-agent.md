# QQ 智能体接管插件 · 技术设计文档

> 状态：**设计稿（未实现）**　最后更新：2026-10-20
> 目标平台：白雾·智能体交互平台 1.5.0

---

## 1. 目标与范围

让智能体**以完整客户端权限接管一个 QQ 账号**：收发消息、看图、发语音、主动发言、修改资料，
并在行为层面模拟真人（随机沉默、打字停顿、资料长期不变）。

**范围之外**：不做 QQ 空间说说（接口支持度待验证，见 §13）、不做语音转文字（平台无 STT）、
不做多账号同时在线（首期单账号，配置按账号维度预留）。

---

## 2. 调研与选型

### 2.1 三条路线

| 方案 | 形态 | 需装 QQ 客户端 | 能否插件内置 | 权限面 | 维护 |
|---|---|---|---|---|---|
| **`@icqqjs/icqq`** | Node 协议库（QQ 安卓协议） | ❌ | ✅ **能** `npm i` 到插件内 | 完整客户端 | 活跃（2026-07 有提交） |
| `Lagrange.Core` | .NET 8 纯协议 + OneBot | ❌ | ⚠️ 需额外 .NET 进程 | 完整客户端 | 活跃（2.9k★） |
| `NapCatQQ` | 基于 NTQQ 客户端 + OneBot 11 | ✅ **需要** | ❌ 独立进程 | 完整客户端 | 活跃 |

### 2.2 选型

**主方案：NapCatQQ（OneBot 11 客户端）**。

原计划用内置协议库 `icqq`，但实测它**没有任何 QQ 空间接口**，而 NapCat 有官方扩展
`POST /send_qzone_msg`（纯文字 / 多图 / 可见范围）。加上 NapCat 基于**真实 NTQQ 客户端**，
风控风险显著低于纯协议实现 —— 因此改用 NapCat 作为主方案。

插件的角色由此变成 **OneBot 11 客户端**：连 NapCat 的 HTTP / WebSocket，业务代码与协议细节解耦。
NapCat 自己负责登录（扫码）与协议维护 —— **QQ 改协议时升级 NapCat 即可，插件不动**。

**可选：`icqq` 内置模式**（已实测可用）。给"不想装第三方软件"的场景留一条路：
插件 `npm i icqq` 后自己扫码登录，跑在 `utilityProcess` 里（Node 20.18.1 验证通过）。
代价：**无说说能力**、风控风险更高。两种模式共用同一套业务层（适配层切换）。

> **实测记录（2026-10-20）**：`icqq@0.6.10` 依赖为**纯 JS + `silk-wasm`**，无原生模块，
> 因此能在 `utilityProcess` 中加载；`setAvatar`/`setSignature`/`sendGroupMsg` 等 7 个 API 均在。
> 但 QQ 空间相关接口**不存在** —— 这是改用 NapCat 的直接原因。

## 3. 总体架构

### 3.1 形态

**Node 侧插件**（`main.js` 跑在 `utilityProcess`），不是 jar 插件。理由：

- 需要**常驻**（与 NapCat 的 WebSocket 长连接）
- 需要**主动触发**（自己判断、自己发消息），jar 插件只有 `before_llm`/`after_llm` 钩子
- Node 插件本来就是完整 Node，`fetch`、定时器、WebSocket 都能用

> **前置依赖**：用户需自行安装 NapCat 并扫码登录 QQ，然后在插件配置里填
> WS 地址（默认 `ws://127.0.0.1:3001`）与 access token。插件本身**不登录 QQ**。

### 3.2 与平台的分工

```
┌──────────────────── 插件（本设计） ────────────────────┐
│  NapCat 连接（OneBot 11 · WS / HTTP）                  │
│  消息归一化 → 闸门 → 决策 → 拟人化发送                  │
│  行为模型（沉默/停顿/冷却）                             │
│  自我管理（头像/签名/状态）                             │
└───────────────┬────────────────────────────────────────┘
                │  api.platform.request（只允许 /api/）
                ▼
┌──────────────────── 平台（不改） ──────────────────────┐
│  POST /api/v1/agent/run   一次智能体运行                │
│  四层记忆（按 sessionId）                               │
│  多模态（parts[] 图片）                                 │
│  工具调用 / RAG / 人格提示词                            │
└────────────────────────────────────────────────────────┘
```

**平台侧改动：0**（唯一待确认项：`utilityProcess` 里能否稳定维持 WS 长连接与自动重连）。

### 3.3 数据流

```
QQ 服务器
   │  消息事件（全量：所有群 + 所有私聊）
   ▼
归一化（text / image / record / at / reply / mface → 统一结构）
   │
   ├─▶ 闸门（白名单 → @/回复 → 群/成员 → 频率）── 不通过 → 丢弃并记日志
   │
   ▼
行为模型（当前状态？静默期？该回吗？）
   │
   ├─▶ 回复：调平台 /agent/run → 拿到文本 → 分段 → 打字节奏 → 发送
   ├─▶ 看图：图片转 base64 → 平台多模态 → 回复 / 发表情包
   └─▶ 主动：决策器判断"值得插话" → 同上发送链路
```

## 4. 能力矩阵（完全鉴权）

> 下表按 **NapCat 的 API 命名**；`icqq` 可选模式下能力基本对等，**唯独没有 `send_qzone_msg`**。

| 能力 | NapCat API | 备注 |
|---|---|---|
| 收私聊 / 群聊（全量） | 事件上报 `message.private` / `message.group` | **"可以选择不理"的前提** |
| 发私聊 / 群聊（主动） | `send_private_msg` / `send_group_msg` | 不需要对方先说话 |
| 发图 / 表情包 | `send_msg` + `image` 段（子类型区分 `mface`） | 表情包走本地库 |
| 发语音 | `send_msg` + `record` 段 | **mp3 直接传，NapCat 转 SILK** |
| @ / 引用 / 撤回 | `at` / `reply` 段、`delete_msg` | |
| 戳一戳 | `send_poke` | 轻互动，适合"试探话题" |
| **改头像** | `set_qq_avatar` | **有审核，可能静默失败** |
| **改昵称** | `set_qq_profile`（`nickname`） | |
| **改签名** | `set_self_longnick`（`longNick`） | |
| **在线状态** | `set_online_status` / `set_diy_online_status` | 支持**自定义状态文案**（"听歌中""摸鱼中"） |
| **"正在输入"** | **`set_input_status`** | ⭐ **拟人化关键**：打字期间让对方看到"正在输入…" |
| 改群名片 | `set_group_card` | 群场景 |
| **发说说（QQ 空间）** | **`send_qzone_msg`** | ⭐ 纯文字 / 多图 / 可见范围（`ugc_right`） |
| 导出 cookie | `get_cookies(domain=...)` | 供空间 / 网页类扩展使用 |
| 群管理 | 踢人 / 设管理 / 全员禁言 | **首期不做**（误操作代价高） |

## 5. 行为模型（拟人化核心）

> 这部分比文案重要。**判定"是不是机器人"靠行为模式，不靠说话内容。**

### 5.1 为什么需要随机化

机器人的特征不是"回答得像不像"，而是**时间规律**：

- 秒回、24 小时在线、每条都回、深夜照样活跃、消息长度高度一致
- 资料常年不变 或者 一天改三次

**真人是不规律的**。所以行为层要主动引入**不规律**。

### 5.2 随机参数表

| 参数 | 默认 | 范围 | 作用 |
|---|---|---|---|
| `replyProbability.private` | 0.9 | 0.6–1.0 | 私聊几乎都回，但**不是 100%** |
| `replyProbability.group` | 0.55 | 0.2–0.9 | 群里**经常不理**（真人也这样） |
| `silenceWindow` | 随机 20–90 分钟 | 5 分钟–4 小时 | **连续不回复任何人**（每天 1–3 次） |
| `firstDelay` | 1.0–4.0 s | 0.5–8 s | 读消息的时间 |
| `charDelay` | 0.03–0.09 s/字 | 0.01–0.15 | 打字速度波动 |
| `pauseAfterPunct` | 0.4–1.2 s | 0.2–2.0 | 标点处**随机停顿** |
| `jitter` | ±0.5 s | ±1.5 | 整体抖动 |
| `segmentGap` | 0.8–2.5 s | 0.5–5 | 多条消息之间 |
| `messageLen` | 8–60 字（正态） | 可配 | 真人不会一次发 500 字 |
| `maxSegments` | 1–3 条 | 1–6 | 长回复拆几条 |
| `onlineWindow` | 07:00–01:00 | 可配 | 深夜不活跃 |
| `profileCooldown.avatar` | **7–30 天随机** | | 换头像后长期不动 |
| `profileCooldown.signature` | **3–14 天随机** | | 同上 |
| `profileCooldown.nickname` | **30–90 天随机** | | 同上 |
| `proactiveGap` | **2–48 小时随机** | | 主动发言间隔，且需话题相关 |

**随机值在配置里写区间，运行时取 `uniform(min, max)`**，并在本地持久化"本次取到的值"，
避免每次重启都重新抽（否则行为模式反而更可疑）。

### 5.3 状态机

```
online   ──随机(每 2–6h)──▶ idle
  ▲                            │
  │     随机(5–40min)          │
  └────────────────────────────┘
  │
  ├── onlineWindow 之外 ──▶ offline（完全不上线）
  │
  └── 收到消息但处于 silenceWindow ──▶ 保持 online，但**不回**
```

| 状态 | 表现 | 触发 |
|---|---|---|
| `online` | 正常回复 | 默认 |
| `idle` | **在线但不回**（消息已读不回） | 随机进入 |
| `busy` | 状态设为"忙碌"，回复概率减半 | 随机 / 手动 |
| `offline` | 不上线 | 时段 + 随机 |
| `silence` | 在线但**全局静默** | 每天 1–3 次，随机 20–90 分钟 |

**关键**：`silence` 与 `idle` 都**必须存在**。永远秒回的账号本身就是异常特征。

### 5.4 打字节奏模型

```js
// 伪代码
async function sendHumanLike(target, text) {
  const segments = splitByPunctuation(text, cfg.maxSegments);
  await sleep(rand(cfg.firstDelay));            // 先"读"一会
  for (const seg of segments) {
    const typing = seg.length * rand(cfg.charDelay) + punctPauses(seg, cfg);

    // ⭐ NapCat 的 set_input_status：让对方看到"正在输入…"
    //    这比单纯 sleep 更像真人 —— 对方能看到你在打，而不是消息凭空出现
    await api('set_input_status', { event_type: 1 });   // 1 = 正在输入
    await sleep(typing + rand(-0.5, 0.5));               // 打字 + 抖动
    await api('set_input_status', { event_type: 0 });    // 停止输入
    await send(target, seg);
    await sleep(rand(cfg.segmentGap));                   // 两条之间
  }
}
```

**注意**：`set_input_status` 的 `event_type` 语义需在 P0 实测（1/0 是否对应"开始/停止输入"）。
若 NapCat 版本不支持，退化为纯 sleep —— 只是少一层拟真，不影响功能。

**必须做**：`typing` 期间如果用户又发了消息，**重新计时**（真人被打断会重新看）。

### 5.5 资料变更冷却

```
改头像 → 记录 ts → 冷却 = uniform(7d, 30d) → 冷却期内拒绝任何头像变更
         → 若换头像失败（审核）→ 额外退避 24h，且 3 次失败后放弃本轮
改签名 → uniform(3d, 14d)
改昵称 → uniform(30d, 90d)
```

**冷却状态必须落盘**（插件私有存储），否则重启后连改三次，比不改更糟。

### 5.6 联系人画像（F14）

平台的四层记忆按 **`sessionId`** 组织，但"这个人在我眼里是谁"**不是记忆，是身份**——
而且平台的长期画像表（`sys_user_fact`）是**平台用户**（`tenant+user`）维度，QQ 联系人是另一套 ID 空间，
不能混进去。所以插件自建一层：

```jsonc
{
  "uin": 123456,
  "alias": "老王",                  // 手动设定，AI 不可改
  "relation": "大学舍友",            // 手动设定，AI 不可改
  "impression": "最近在准备考研，压力大，不喜欢被问进度",
  "source": "auto",                 // auto | manual
  "confidence": 0.7,
  "updatedAt": "2026-10-20T12:00:00Z",
  "messageCount": 128
}
```

| 来源 | 写入什么 | 覆盖规则 |
|---|---|---|
| 用户手动 | `alias` / `relation` / `impression` | **AI 永不覆盖手动字段** |
| AI 总结 | 只写 `impression`（`source: auto`） | 手动已有 `impression` 时，**写入候选**并提示，不直接生效 |

**注入方式**：每次调 `/agent/run` 前，把画像拼成一段前缀：

```
【关于正在和你聊天的人】
他是 老王（大学舍友）。你与他的印象：最近在准备考研，压力大，不喜欢被问进度。
```

**为什么不塞进平台记忆**：平台的 `sys_user_fact` 是 `(tenant, user)` 维度，
QQ 联系人是 `uin` 维度。混进去会让"平台用户画像"被聊天对象污染。

**总结时机**：该联系人累计 ≥ N 条消息（默认 20）且距上次总结 ≥ 3 天，才重新总结一次 ——
避免每轮都调模型烧 token，也避免画像频繁变动。

## 6. 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| **F1** | 登录：内置 `@icqqjs/icqq` 扫码登录 | 单账号；配置结构预留多账号 |
| **F1b** | 备选接入：OneBot 11（NapCat / Lagrange） | 地址 + token；业务逻辑不变 |
| **F2** | 私聊：白名单联系人自动回复 | 白名单为空 = 全部忽略（**默认安全**） |
| **F3** | 群聊四层闸门：`@或回复` → 群白名单 → 成员白名单 → 频率 | 缺任一层都可能被群消息烧光 token |
| **F4** | 多人格提示词，可切换；人格作用于平台智能体 | 复用平台人格，插件只做映射 |
| **F5** | 拟人化：消费 §5 行为模型 | 分段 / 延迟 / 停顿 / 静默 |
| **F6** | 视觉：收图转 base64 → 平台多模态；发表情包（本地库 + 情绪标签） | 表情包目录可配 |
| **F7** | 语音：文本 → TTS（插件自带 key）→ mp3 → `record` | **不做语音转文字** |
| **F8** | 主动发言：消息流驱动 + 记忆驱动，**不用定时器** | 见 F12 |
| **F9** | **发说说**：`send_qzone_msg`（文字 / 图片 / 可见范围） | **仅 NapCat 模式可用**；受 F13 节流与内容审核约束 |
| **F10** | 记忆：每联系人/群独立 `sessionId` | `qq:private:<qq>:<uin>` / `qq:group:<qq>:<gid>` |
| **F11** | 自我管理：头像 / 昵称 / 签名 / 在线状态 | 受 §5.5 冷却约束 |
| **F12** | 主动决策器：小模型判断"这条要不要插话" | 输入 = 最近 N 条 + 人格 + 记忆摘要 |
| **F13** | 行为节流：主动发言 / 改资料 / 模型调用都有上限 | 见 N2、N6 |
| **F14** | **联系人画像**：每个 QQ 联系人在智能体眼里是谁 | 见 §5.6 |

## 7. 非功能需求

| 编号 | 要求 |
|---|---|
| **N1** | 首次启用弹**风险确认**：协议登录违反 QQ 用户协议、有封号风险，建议小号 |
| **N2** | 成本护栏：每分钟最多 N 次模型调用（默认 6），超限丢弃并记日志 |
| **N3** | 断线重连：指数退避（1s→2s→4s…上限 60s），重连后**不补发历史消息** |
| **N4** | 平台 0 改动（除 `utilityProcess` 兼容性验证） |
| **N5** | 可观测：每条消息记录「收到 / 被哪一层闸门拦下 / 是否回复 / 耗时」，能回答"为什么没回" |
| **N6** | **一键停手**：一个开关立刻停止所有自主行为（发消息、改资料），只保留收消息 |

## 9. 关键流程

### 9.1 收到一条消息

```
1. 归一化（text/image/record/at/reply/mface）
2. 闸门：
   a. 私聊 → 白名单命中？
   b. 群聊 → @或reply？ → 群在白名单？ → 成员在白名单？
   c. 频率未超限？
   → 任一不通过：记日志（原因）并返回
3. 行为模型：当前状态？silence 中？该回吗（replyProbability）？
   → 不该回：记日志并返回
4. 调平台 /agent/run（带 sessionId、parts[]、人格）
5. 拟人化发送（§5.4）
6. 更新统计（该会话回复次数、时间戳）
```

### 9.2 主动发言

```
触发源（二选一，不用定时器）：
  ① 消息流：群/私聊出现新话题 → 小模型判断"我能接吗"
  ② 记忆：从长期记忆召回"某人的近况" → 判断"该问一句吗"
约束：
  - 距离上次主动发言 ≥ uniform(2h, 48h)
  - 该会话最近未被自己刷屏（近 1h 内主动发言 ≤ 1 次）
  - killSwitch 关闭
  - 命中后仍走"拟人化发送"
```

### 9.3 自我管理

```
1. 触发：模型在回复里表达"想换个头像"（或定期低频检查）
2. 冷却检查：profileCooldown.avatar 未到 → 拒绝，记日志
3. 取图：网络搜索 / 平台图片生成
4. setAvatar(file)
5. 结果校验：**QQ 头像审核是异步的** → 延迟 N 分钟后读回当前头像 URL 比对
6. 失败：退避 24h，累计 3 次失败则本轮放弃并告警
```

### P2 落地时踩到的四个坑（都值得记下）

1. **`extra.images` 被厂商静默丢弃**：图片原来塞在 `ChatRequest.extra` 这个"透传口袋"里，
   而它会被原样 `putAll` 进请求体 —— 厂商不认识 `images` 字段，直接忽略。
   表现是"图上传成功、模型说看不到"。**必须转成标准 `content: [{type:image_url}]`**。
2. **分段正则缺 `m` 标志会吃掉前面的行**：用户给的 `.*?[。？！~…]+|.+$`，在没有 `m` 时
   `$` 只匹配字符串末尾、`.` 不匹配换行 → `. +$` 只匹配最后一行。
   模型答了 `1+1 = 2\n2+2 = 4`，QQ 上只收到后者，**看起来像模型只答了一题**（连续误判三轮）。
3. **Markdown 泄漏**：平台默认在系统提示词尾部注入「输出格式」指引（教模型用 Markdown），
   纯文本渠道必须传 `renderGuide=false`，否则 `**` `-` `|` 全变字面符号。
4. **列表符号不要"美化"**：把 `- ` 替换成 `· ` 等于凭空给 QQ 加了个它本来没有的符号 —— 直接删掉前缀即可。
| **P2 多模态** | F6/F7 | 看图、发语音、发表情包 | 图片能被模型理解 |
| **P3 主动** | F8/F11/F12/F13 | 主动发言、改资料、节流 | 连续 72h 行为不过于规律 |
| **P4 观察** | 小号实跑 | 风控报告 | 无异常再上主号 |

**P0 不通过就停**：换 OneBot 方案重做 P0，不要先写业务代码。

## 14. 未实现的架构方案：让 AI 自主收发消息

> **当前实现是方案 B**（见 §14.3）：插件缓存群聊最近 20 条，被 @ 时一并交给模型，
> 模型用 `[SILENT]` 决定接不接。**零平台改动**，覆盖了"选择性参与"这个核心体验。
>
> A / C 两个方案没有实现，但迟早会被问到"为什么不让 AI 自己决定什么时候去看消息"，
> 所以把设计与代价写在这里。

### 14.1 方案 A：插件开本地 HTTP 端点，平台专用工具回调

**插件侧**

```js
// 1. 监听随机端口（系统分配，避免冲突）
const server = http.createServer(router);
server.listen(0, '127.0.0.1', async () => {
  const port = server.address().port;
  const token = crypto.randomUUID();          // 一次性凭证
  // 2. 把端点注册给平台
  await api.platform.request({
    path: `/api/v1/plugin-web/${api.pluginId}/endpoint`,
    method: 'POST',
    body: { port, token },
  });
});

// 3. 端点（全部校验 Bearer token）
// GET  /messages?limit=20   -> [{ chatType, peer, sender, text, at }]
// POST /send                -> { target, text }  -> 走 NapCat
// GET  /status              -> { connected, uin, nickname }
```

**平台侧**

1. 新增 `POST /api/v1/plugin-web/{id}/endpoint`，把 `{port, token}` 存下来（内存或库）。
2. 新增两个工具（内置插件形式）：`qq_get_unread_messages` / `qq_send_message`。
3. 工具执行时读出端点 → 转发 HTTP → 把结果包成 `ToolResult`。

**必须解决的问题（这才是成本所在）**

| 问题 | 说明 |
|---|---|
| **端点失效** | 插件重启后端口会变，平台侧旧端点要能识别为失效并提示，而不是让工具一直超时 |
| **凭证存放** | token 存内存则平台重启丢失，存库则要加密。两条都有代价 |
| **超时预算** | 工具调用有超时（模型在等），插件必须在预算内返回；NapCat 抖动会直接变成"工具失败" |
| **单实例** | 同一插件只能有一个端点；重复注册要覆盖还是拒绝，得定 |
| **安全** | 本地端口任何进程都能连 → 必须只绑 `127.0.0.1` + 强制 Bearer token |
| **跨进程失败模式** | 原来是进程内函数调用，现在多了网络跳：连接拒绝 / 半开 / 响应截断 都要处理 |

**结论**：这不是"加几十行"，而是**一个跨进程 RPC 子系统**。

### 14.2 方案 C：平台工具代理（`proxy.url`）

**平台侧（plugin-sdk）**

```java
record PluginTool(String name, String description, ObjectNode inputSchema,
                  ToolHandler handler, String proxyUrl) { }

// ToolExecutor.run 里加一个分支
if (tool.proxyUrl() != null) {
    // 转发 HTTP POST，body = args，超时 10s
    // 非 2xx / 超时 / 连接失败 -> ToolResult.fail(可读的原因)
} else {
    tool.handler().handle(args, ctx);   // 本地执行
}
```

**插件侧**：仍要提供 HTTP 端点（同 A），只是工具的"外壳"由平台统一注册。

**改动面**

- `PluginTool`：加字段 → **所有构造点都要改**（含测试）
- `ToolExecutor`：加分支 + 超时 + 错误映射
- 端点注册：同 A（平台仍需知道插件的端口）
- 测试：要覆盖"代理超时 / 非 2xx / 插件未启动"

**它比 A 好在哪**：插件可以把自己任意能力暴露成工具（不必为每个能力在平台上写一个 Java 类）。
**它比 A 差在哪**：改的是**平台的工具执行主链路**，影响所有插件；A 只影响新加的两个工具。

### 14.3 三方案对比

| | **A：插件端点 + 专用工具** | **B：上下文扩展（已实现）** | **C：工具代理** |
|---|---|---|---|
| 平台改动 | 中（2 个工具 + 端点注册接口） | **零** | **大**（SDK + 执行器主链路） |
| 插件改动 | 中（HTTP 服务 + 鉴权 + 端点注册） | **小（内存缓冲 20 条）** | 中 |
| AI 主动拉新消息 | ✅ | ❌（等人 @ 或心跳） | ✅ |
| AI 选择性参与 | ✅ | ✅（`[SILENT]`） | ✅ |
| 失败模式 | 多（跨进程） | **少（纯内存）** | 多 |
| 何时值得做 | 需要"AI 自己巡检群消息"时 | 现在 | 需要插件暴露**任意**工具时 |

### 14.4 为什么先选 B

1. **它覆盖了核心体验**：群里 50 条闲聊只回 1 条 —— 靠的是"看到上下文 + `[SILENT]`"，
   而不是"AI 自己去拉"。
2. **A/C 的额外能力与「主动发言」重叠**：没人找它时，心跳已经在给它开口的机会。
3. **代价差一个量级**：B 是几十行内存代码，A/C 是跨进程调用 + 鉴权 + 失败处理 + 测试。

**什么时候该回头做 A**：当你发现"它应该主动去看群里在聊什么，而不是等人 @"这种需求反复出现，
且心跳式的主动发言满足不了 —— 那时再上 A，也有具体依据。
